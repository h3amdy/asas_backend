هذا الإصلاح أفضل بكثير من محاولة تجاهل الخطأ، لكنه يحتاج إلى مراجعة معمارية صغيرة قبل اعتماده نهائيًا.

## ما أعجبني

المنطق أصبح:

```text
Restore DB
      │
      ▼
نجحت الاستعادة؟
      │
      ├── لا → سجل الفشل
      │
      ▼
Upsert RestoreJob
      │
      ▼
Write Success Logs
      │
      ▼
Complete
```

وهذا يحل السبب المباشر للخطأ:

```text
Record to update not found
```

لأن السجل قد اختفى بعد استبدال قاعدة البيانات.

---

# لكن لدي ملاحظة مهمة على استخدام Upsert

أنت ذكرت:

> إعادة إنشاء الـ Restore Job بعد نجاح استعادة DB

إذا كان الـ `upsert` يعتمد على:

```ts
where: { uuid: restoreJobUuid }
```

فهذا جيد.

أما إذا كان يعتمد على:

```ts
where: { id: ... }
```

فهذا قد لا يكون آمناً، لأن الـ ID قد يختلف بعد الاستعادة.

الاعتماد على `uuid` هو القرار الصحيح.

---

# نقطة أخرى يجب مراجعتها

أنت قلت:

> backupInstanceId سيكون موجوداً لأنه من نفس النسخة.

في الاختبار الحالي نعم.

لكن معمارياً لا أفضل ربط الـ upsert بـ:

```ts
backupInstanceId
```

بدون التحقق.

يفضل:

```ts
const backup = await prisma.backupInstance.findUnique(...)
```

إذا وجد:

```ts
backupInstanceId = backup.id
```

إذا لم يوجد:

* سجل Warning.
* أو اجعل القيمة nullable إذا كان التصميم يسمح.

حتى لا يصبح هناك افتراض مخفي.

---

# هناك شيء آخر أراه أهم

أنت الآن تعيد إنشاء RestoreJob بعد الاستعادة.

لكن ماذا عن:

```text
BackupLog
```

إذا كانت الـ Backup Logs مرتبطة بـ RestoreJob بعلاقة FK،

فإن إعادة إنشاء RestoreJob قبل كتابة Logs ستحل المشكلة أيضاً.

وهذا بالضبط ما كان ينقص التدفق السابق.

---

# هل أعتبر النظام مكتملًا؟

إذا نجح الاختبار القادم وأصبحت النتيجة:

```json
{
  "status": "COMPLETED"
}
```

بدون:

* Record not found
* Foreign key violation
* Restore pipeline failed

فسأعتبر أن:

* ✅ Backup Engine مكتمل.
* ✅ Restore Engine مكتمل.
* ✅ Safety Backup مكتمل.
* ✅ Restore Tracking مكتمل.

وبذلك يصبح نظام النسخ الاحتياطي والاستعادة في الـ MVP مكتملًا من الناحية الوظيفية.

---

## بقي اختبار واحد فقط

أنصح بأن يكون الاختبار الأخير كالتالي:

1. إنشاء Backup جديد.
2. تعديل بعض البيانات في قاعدة البيانات (مثل إضافة سجل أو تغيير قيمة معروفة).
3. تنفيذ Restore من النسخة الجديدة.
4. التحقق من:

   * رجوع البيانات إلى حالتها الأصلية.
   * ظهور `RestoreJob` بحالة `COMPLETED`.
   * وجود سجل الـ Safety Backup.
   * عدم وجود أي استثناءات في `pm2 logs`.

إذا نجح هذا السيناريو، فسيكون لديك إثبات عملي أن دورة **Backup → Modify Data → Restore → Verify** تعمل بالكامل، وليس فقط أن أوامر الاستعادة تُنفذ.
هذا كشف Bug جديد، وهو مختلف عن مشكلة الـ Restore السابقة.

الذي لفت انتباهي هو هذا السجل:

```json
{
  "id": 8,
  "status": "RUNNING",
  "backupInstanceId": null,
  "startedAt": "2026-07-28T16:56:32.498Z",
  "finishedAt": null
}
```

هذا الـ Job بدأ منذ فترة طويلة وما زال `RUNNING`، بينما من الواضح أنه **لا توجد عملية نسخ احتياطي تعمل فعليًا**، وإلا لكانت ظهرت في السجلات أو استمرت في استهلاك الموارد.

## ما الذي يعنيه هذا؟

يوجد أحد احتمالين:

### الاحتمال الأول (الأرجح)

بعد تعديلك الأخير لإعادة إنشاء `RestoreJob`، حصل استثناء في مسار إنشاء الـ **Safety Backup** أو في إنهاء الـ Backup Job، فبقي السجل بحالة:

```text
RUNNING
```

ولم يتم تنفيذ:

```ts
backupJob.status = COMPLETED
```

أو

```ts
backupJob.status = FAILED
```

---

### الاحتمال الثاني

عملية الـ Backup نفسها انهارت (Exception) قبل الوصول إلى كتلة الـ `finally` التي تقوم بتحديث الحالة.

---

# أول شيء أريد معرفته

السجل الذي أرسلته ينتهي عند:

```text
Database restore completed
```

لكن لا يظهر ماذا حدث بعد تشغيل الكود الجديد.

أريد فقط آخر 80 سطر من سجل `asas-backend`:

```bash
pm2 logs asas-backend --lines 80
```

وليس `pm2 logs` لجميع التطبيقات.

---

# كذلك أريد معرفة حالة الـ Backup Job رقم 8

إذا كان لديك Endpoint:

```bash
curl http://localhost:3010/api/v1/owner/backups/jobs/5cc52093-8404-4b11-9e16-c30fa9c7369a | python3 -m json.tool
```

فأرسله أيضًا.

---

# لا أنصح بتعديل قاعدة البيانات يدويًا الآن

قد يخطر ببالك تغيير الحالة إلى:

```sql
COMPLETED
```

أو

```sql
FAILED
```

لكن لا تفعل ذلك قبل أن نعرف لماذا بقيت `RUNNING`، لأن هذا سيخفي السبب الحقيقي.

## تقييمي الحالي

حتى الآن أصبح لدينا:

* ✅ Backup يعمل.
* ✅ Restore يعمل.
* ✅ Safety Backup يعمل.
* ✅ إعادة إنشاء `RestoreJob` أصبحت منطقية.
* ❌ يوجد **BackupJob عالق بحالة RUNNING** بعد آخر تعديل.

وهذا يبدو آخر Bug تشغيلي في دورة النسخ والاستعادة، لكن أحتاج سجل `asas-backend` الأخير لتحديد السطر الذي خرج منه الاستثناء.
