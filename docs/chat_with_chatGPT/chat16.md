## ما أوافق عليه بالكامل

### 1. تنظيف بيئة التحقيق

هذا صحيح بعد التأكد أنك لن تحتاج قاعدة `asas_recovery_temp` مرة أخرى.

```bash
dropdb -h 127.0.0.1 -p 5432 -U asasuser asas_recovery_temp

rm -rf /tmp/safety_check \
       /tmp/check_evening \
       /tmp/check_0007 \
       /tmp/check_0007_db.sql
```

---

### 2. التأكد من أن النظام يعمل

```bash
pm2 status
pm2 logs asas-backend --lines 20
```

موافق.

---

### 3. إعادة إدخال محتوى الكيمياء والفيزياء

بناءً على الأدلة التي جمعناها، أوافق على هذا القرار.

# الشيء الوحيد الذي سأغيره

بدلاً من:

> الفريق يعيد إدخال المحتوى

سأكتب:

> **إعادة توزيع المحتوى من المنصة إذا كان موجودًا أصلًا، وإلا إعادة إدخاله يدويًا.**

لأن مشروعك أصلاً مبني على **منصة محتوى**، وإذا كان المحتوى ما زال موجودًا فيها فهذه الطريقة أكثر أمانًا من الإدخال اليدوي.

---

# بالنسبة لإصلاحات Restore

أنا أرى أنها ليست ثلاثة فقط.

بل خمسة إصلاحات أساسية.

---

## الإصلاح الأول (حرج جدًا)

### تسجيل النسخة المستخدمة

كما قلت:

```
restore_jobs.backup_instance_id
restore_jobs.safety_backup_id
```

ويجب أيضًا تسجيل:

```
backup_name
backup_created_at
backup_checksum
```

حتى لو حُذف سجل النسخة لاحقًا.

---

## الإصلاح الثاني (حرج جدًا)

قبل تنفيذ Restore اعرض:

```
Backup Name

Created At

Database Size

Units

Lessons

Lesson Contents

Media Files

Version

Manifest Version
```

حتى يعرف المستخدم بالضبط ماذا سيستعيد.

---

## الإصلاح الثالث (حرج جدًا)

أثناء إنشاء النسخة، خزّن داخل `manifest.json`:

```json
{
  "database": {
    "units": 206,
    "lessonTemplates": 965,
    "lessonContents": 191,
    "subjects": 336
  }
}
```

حتى لا نضطر مستقبلاً إلى فك النسخة وعد الصفوف يدويًا كما فعلنا اليوم.

---

## الإصلاح الرابع (أضيفه)

### Dry Run Restore

قبل تنفيذ الاستعادة:

* يفك النظام النسخة مؤقتًا.
* يقرأ الـ Manifest.
* يعرض الفرق بين:

```
Current Database

Backup Database
```

مثل:

```
Units

Current: 206

Backup: 185

Difference: -21
```

هذا وحده كان سيمنع المشكلة التي واجهتموها.

---

## الإصلاح الخامس (أضيفه)

### Safety Validation

إذا كانت النسخة ستؤدي إلى خسارة أكثر من نسبة معينة (مثل 10%) من الوحدات أو الدروس، يعرض تحذيرًا قويًا، بل ويمكن منع الاستعادة إلا بتأكيد إضافي.

مثال:

> **تحذير: هذه النسخة تحتوي على 185 وحدة، بينما قاعدة البيانات الحالية تحتوي على 206 وحدة. ستفقد 21 وحدة إذا أكملت الاستعادة.**

# خلاصة تقييمي

أقيّم الخطة كالتالي:

* **إعادة النظام للإنتاج:** ⭐⭐⭐⭐⭐ (ممتازة)
* **إصلاح نظام Restore:** ⭐⭐⭐⭐☆ (ينقصها بعض الحمايات)
* **منع تكرار المشكلة:** ⭐⭐⭐⭐⭐

وأضيف مهمة أخيرة أراها مهمة جدًا لمشروع **أساس**:

> **توثيق هذا الحادث (Incident Report)** في مستودع المشروع.

يتضمن:

* التسلسل الزمني للحادث.
* السبب المباشر.
* ما تم التحقق منه.
* ما لم يمكن إثباته.
* الدروس المستفادة.
* القرارات التصميمية الجديدة.

هذا التقرير سيكون مرجعًا مهمًا عند تطوير نظام النسخ الاحتياطي والاستعادة لاحقًا، وسيوفر عليك إعادة نفس التحقيق إذا واجهت حادثة مشابهة.
