# الشيء الوحيد الذي سأغيره

بدلاً من:

> الفريق يعيد إدخال المحتوى

سأكتب:

> **إعادة توزيع المحتوى من المنصة إذا كان موجودًا أصلًا، وإلا إعادة إدخاله يدويًا.**

لأن مشروعك أصلاً مبني على **منصة محتوى**، وإذا كان المحتوى ما زال موجودًا فيها فهذه الطريقة أكثر أمانًا من الإدخال اليدوي.

# بالنسبة لإصلاحات Restore

أنا أرى أنها ليست ثلاثة فقط.

بل خمسة إصلاحات أساسية.

---

## الإصلاح الأول (حرج جدًا)

### تسجيل النسخة المستخدمة

كما قلت:

```
restore_jobs.backup_instance_id
restore_jobs.safety_backup_id
```

ويجب أيضًا تسجيل:

```
backup_name
backup_created_at
backup_checksum
```

حتى لو حُذف سجل النسخة لاحقًا.

---

## الإصلاح الثاني (حرج جدًا)

قبل تنفيذ Restore اعرض:

```
Backup Name

Created At

Database Size

Units

Lessons

Lesson Contents

Media Files

Version

Manifest Version
```

حتى يعرف المستخدم بالضبط ماذا سيستعيد.

---

## الإصلاح الثالث (حرج جدًا)

أثناء إنشاء النسخة، خزّن داخل `manifest.json`:

```json
{
  "database": {
    "units": 206,
    "lessonTemplates": 965,
    "lessonContents": 191,
    "subjects": 336
  }
}
```

حتى لا نضطر مستقبلاً إلى فك النسخة وعد الصفوف يدويًا كما فعلنا اليوم.

---

## الإصلاح الرابع (أضيفه)

### Dry Run Restore

قبل تنفيذ الاستعادة:

* يفك النظام النسخة مؤقتًا.
* يقرأ الـ Manifest.
* يعرض الفرق بين:

```
Current Database

Backup Database
```

مثل:

```
Units

Current: 206

Backup: 185

Difference: -21
```

هذا وحده كان سيمنع المشكلة التي واجهتموها.

---

## الإصلاح الخامس (أضيفه)

### Safety Validation

إذا كانت النسخة ستؤدي إلى خسارة أكثر من نسبة معينة (مثل 10%) من الوحدات أو الدروس، يعرض تحذيرًا قويًا، بل ويمكن منع الاستعادة إلا بتأكيد إضافي.

مثال:

> **تحذير: هذه النسخة تحتوي على 185 وحدة، بينما قاعدة البيانات الحالية تحتوي على 206 وحدة. ستفقد 21 وحدة إذا أكملت الاستعادة.**

# خلاصة تقييمي

أقيّم الخطة كالتالي:

* **إعادة النظام للإنتاج:** ⭐⭐⭐⭐⭐ (ممتازة)
* **إصلاح نظام Restore:** ⭐⭐⭐⭐☆ (ينقصها بعض الحمايات)
* **منع تكرار المشكلة:** ⭐⭐⭐⭐⭐

وأضيف مهمة أخيرة أراها مهمة جدًا لمشروع **أساس**:

> **توثيق هذا الحادث (Incident Report)** في مستودع المشروع.

يتضمن:

* التسلسل الزمني للحادث.
* السبب المباشر.
* ما تم التحقق منه.
* ما لم يمكن إثباته.
* الدروس المستفادة.
* القرارات التصميمية الجديدة.

هذا التقرير سيكون مرجعًا مهمًا عند تطوير نظام النسخ الاحتياطي والاستعادة لاحقًا، وسيوفر عليك إعادة نفس التحقيق إذا واجهت حادثة مشابهة.
راجعت التعديلات المعروضة في الصور، وأرى أنها **تسير في الاتجاه الصحيح جدًا**، بل إنها تعالج مباشرةً الدروس المستفادة من الحادثة التي مررتم بها. ومع ذلك لدي بعض الملاحظات حتى يصبح التصميم أقوى.

# ما أعجبني

## 1. حفظ إحصاءات المحتوى داخل Manifest ✅

أنت تضيف:

```ts
contentStats: {
    totalUnits,
    totalLessons,
    totalContents,
    totalQuestions,
    capturedAt,
}
```

وهذا بالضبط ما كنا نفتقده أثناء التحقيق.

بدلاً من:

> نفك الـ tar
>
> ثم نفك postgres.sql.gz
>
> ثم نعد الأسطر داخل COPY

سيصبح لدينا:

```json
{
  "contentStats": {
    "totalUnits": 206,
    "totalLessons": 965,
    "totalContents": 191,
    "totalQuestions": 5210
  }
}
```

وهذا ممتاز.

---

## 2. أخذ الإحصاءات وقت إنشاء النسخة وليس بعد الانتهاء

لاحظت أنك تحسبها قبل `buildManifest`.

هذا صحيح.

لأنها تمثل **لحظة أخذ النسخة**.

وليس بعد دقائق من انتهاء ضغط الملفات.

---

## 3. تسجيل Safety Backup في Restore Job

هذه الإضافة:

```ts
safetyBackupId: safetyBackupId
```

كنت أعتبرها من أهم النواقص.

الآن سيكون لديك سلسلة واضحة:

```
Restore Job
      ↓
Backup المستخدمة
      ↓
Safety Backup التي أُنشئت
```

وهذا ممتاز.

---

## 4. Post Restore Verification

لاحظت أنك أضفت:

```ts
const [unitsCount, lessonsCount, contentsCount]
```

ثم:

```
Post-restore stats
```

هذا جيد جدًا.

سيجعل الـ logs مفيدة عند التحقيق.

# لكن لدي 5 اقتراحات

---

# ① لا تحفظ العدادات فقط

بدلاً من:

```json
{
  "totalUnits":206
}
```

احفظ أيضًا نسخة التطبيق.

مثلاً:

```json
{
  "schemaVersion": 10,
  "appVersion": "1.4.2",
  "migration": "20260307000646",
  "contentStats": { ... }
}
```

---

# ② أضف حجم قاعدة البيانات

داخل manifest:

```json
{
    "database": {
        "sizeBytes": 981273456
    }
}
```

أحيانًا الفرق في الحجم يكشف مشكلة قبل الاستعادة.

---

# ③ أضف Soft Deleted

أنت الآن تعد:

```ts
isDeleted = false
```

لكن أثناء التحقيق احتجنا أن نعرف أيضًا:

```
deletedUnits

deletedLessons

deletedContents
```

لذلك أفضّل:

```json
{
    "activeUnits":206,
    "deletedUnits":5
}
```

بدلاً من رقم واحد فقط.

---

# ④ المقارنة يجب ألا تكون في Logs فقط

أهم شيء خرجنا به من الحادثة هو:

> لا نريد أن يقرأ المطور الـ log.

بل نريد أن يرى المستخدم:

```
Current DB

Units: 206

Backup

Units: 185

⚠ ستفقد 21 وحدة
```

أي أن Manifest لا يكفي.

يجب استغلاله داخل شاشة Restore.

---

# ⑤ أقوى إضافة (أنصح بها جدًا)

بدلاً من:

```
contentStats
```

أضف أيضًا:

```json
{
    "fingerprint":{
        "unitsChecksum":"...",
        "lessonsChecksum":"..."
    }
}
```

مثلاً:

```
SHA256
```

لقائمة UUID الخاصة بالوحدات.

لأن العدادات وحدها لا تكشف كل شيء.

قد يكون لديك:

```
206 وحدة
```

لكنها ليست نفس الـ 206.

وجود بصمة (Fingerprint) يساعد على اكتشاف اختلاف المحتوى حتى لو كانت الأعداد متساوية.

---

# تقييمي

لو كانت النسخة السابقة من النظام:

**7/10**

فبعد هذه التعديلات أصبحت تقريبًا:

**9.3/10**

وأعتقد أن الشيء الوحيد المتبقي ليصبح النظام احترافيًا فعلًا هو **مرحلة ما قبل الاستعادة (Pre-Restore Analysis)**.

أي:

```
اختر النسخة

↓

اقرأ manifest

↓

قارن مع قاعدة البيانات الحالية

↓

اعرض الفروقات

↓

اطلب التأكيد

↓

أنشئ Safety Backup

↓

Restore

↓

Post Verification
```

برأيي هذه ستكون آخر قطعة كبيرة تجعل نظام النسخ الاحتياطي والاستعادة في مشروع **أساس** قويًا وموثوقًا للاستخدام في بيئة الإنتاج.
