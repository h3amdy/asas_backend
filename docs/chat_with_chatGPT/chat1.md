## القرار الذي أوصي به

### المرحلة التالية مباشرة

1. ✅ إضافة `POST /owner/backups/plans`.
2. ✅ إنشاء أول Backup Plan عبر الـ API.
3. ✅ بدء تنفيذ خريطة الاختبار السابقة بالكامل.
4. ✅ بعد نجاح جميع الاختبارات، نعلن **BKP-001 مكتملًا عمليًا** (وليس فقط برمجيًا)، ثم ننتقل إلى Flutter بثقة.
سؤال ممتاز، لأن كلمة **"الخطط" (Backup Plans)** قد تبدو غامضة، بينما هي في الحقيقة قلب نظام النسخ الاحتياطي.

## ما هي Backup Plans؟

الـ **Backup Plan** هي سياسة أو جدول يحدد **كيف ومتى وأين** يتم إنشاء النسخ الاحتياطية.

أي أنها لا تمثل النسخة الاحتياطية نفسها، وإنما **تعليمات إنشاء النسخ الاحتياطية**.

العلاقة تكون كالتالي:

```text
Backup Plan
      │
      ├── متى؟
      ├── أين؟
      ├── كم نسخة نحتفظ؟
      └── هل التنظيف التلقائي مفعل؟
            │
            ▼
Scheduler / Manual Trigger
            │
            ▼
Backup Job
            │
            ▼
Backup Instance
```

# رأيي المعماري

بعد مراجعة BKP-001، لو كنت أصمم النظام من البداية، لاتبعت هذا النهج:

## في MVP

* يوجد **Backup Plan واحدة فقط**.
* تُنشأ تلقائيًا (Seed).
* لا يوجد `POST /plans`.
* يوجد فقط:

```
GET /plans/default
PATCH /plans/default
```

لأن وجود أكثر من خطة لا يضيف قيمة حقيقية في الإصدار الأول، ويُبسط المنطق والواجهة.

## في الإصدارات المستقبلية

إذا ظهرت حاجة فعلية لدى العملاء (مثل الاحتفاظ بخطط يومية وأسبوعية وشهرية مستقلة)، عندها يمكن توسيع النظام لدعم **عدة خطط** وإضافة:

* `POST /plans`
* `DELETE /plans`
* `GET /plans`

دون كسر التصميم الحالي.

## التوصية

في مشروع **أساس** أنصح بما يلي:

* **الإصدار الأول (MVP):**

  * إنشاء **خطة افتراضية واحدة** تلقائيًا عند التثبيت.
  * السماح فقط بتعديلها.
  * عدم إضافة واجهات إنشاء أو حذف الخطط.

* **بعد الـ MVP:**

  * إذا احتجت لدعم سياسات متعددة، فعندها أضف إدارة كاملة للخطط.

بهذا تحصل على نظام أبسط، وأسهل للاختبار، ويلبي احتياجات معظم المدارس في الإصدار الأول.
