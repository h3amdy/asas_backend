# قبل أن نبدأ الكتابة

هناك قرار معماري مهم يجب حسمه أولًا لأنه سيؤثر على التصميم بالكامل:

> **هل ستكون الاستعادة "استبدالًا كاملًا" (Destructive Restore)، بحيث تحذف البيانات الحالية ثم تستعيد النسخة الاحتياطية، أم ستُجبر دائمًا على الاستعادة إلى قاعدة بيانات ومجلد وسائط جديدين بحيث لا تُلمس البيئة الحالية؟**

بالنسبة لمشروع **أساس**، أميل إلى دعم **الطريقتين**:

* **Restore إلى بيئة جديدة** للاختبار والتحقق (الأكثر أمانًا).
* **Restore فوق البيئة الحالية** بعد تأكيد صريح من مالك المنصة عند الحاجة الفعلية للتعافي من كارثة.

إذا اتفقنا على هذا القرار، فسنبني بقية وثيقة **BKP-002 Restore SRS** على أساس واضح ومستقر.
ممتاز. إذن سنبنيها بنفس منهجية بقية أنظمة مشروع **أساس**: نبدأ بالتحليل ثم SRS ثم Use Cases ثم API ثم التنفيذ.

لكن قبل كتابة أي سطر، أريد تثبيت فلسفة النظام حتى لا نغيرها لاحقًا.

# BKP-002 Restore System

## الهدف

تمكين **مالك المنصة (Platform Owner)** من استعادة نسخة احتياطية كاملة أو جزئية بطريقة آمنة وموثوقة، مع حماية البيانات الحالية ومنع أي استعادة غير صالحة.

---

# المبادئ الأساسية

## 1. الاستعادة عملية خطيرة

على عكس النسخ الاحتياطي، فإن الاستعادة تغير بيانات النظام.

لذلك يجب أن تكون:

* محمية.
* قابلة للتتبع.
* قابلة للإلغاء قبل البدء.
* لا تبدأ إلا بعد عدة عمليات تحقق.

---

## 2. لا توجد استعادة مباشرة

لن يقوم النظام مباشرة بتنفيذ:

```text
Restore
```

بل سيمر بالمراحل التالية:

```text
اختيار النسخة
        ↓
قراءة Manifest
        ↓
التحقق من الإصدار
        ↓
التحقق من Checksum
        ↓
التحقق من المساحة
        ↓
تأكيد المستخدم
        ↓
Restore
```

---

## 3. نوعا الاستعادة

### أولا: Restore إلى بيئة جديدة (Restore to New Environment)

مثلاً:

```
Production
```

يبقى كما هو.

ويتم إنشاء:

```
Database:
asas_restore_test

Media:
/www/media-storage-restore/
```

هذا مناسب لـ:

* الاختبار.
* التحقق.
* التدريب.

---

### ثانياً: Restore فوق البيئة الحالية (In-place Restore)

هذه هي استعادة الطوارئ.

قبل التنفيذ يجب أن يعرض النظام تحذيرًا واضحًا مثل:

> سيتم استبدال البيانات الحالية بالكامل. لا يمكن التراجع عن هذه العملية.

ثم يطلب تأكيدًا صريحًا من مالك المنصة.

---

# أنواع الاستعادة

أقترح أن يدعم النظام أربعة أنواع:

### Full Restore

* Database
* Media
* Config

---

### Database Only

لا يلمس الوسائط.

---

### Media Only

لا يلمس قاعدة البيانات.

---

### Config Only

يستعيد ملفات الإعداد فقط.

---

# مراحل التنفيذ

أرى أن محرك الاستعادة يجب أن يمر بـ 10 مراحل:

```
1. Acquire Lock

↓

2. Read Manifest

↓

3. Verify Backup Version

↓

4. Verify Checksum

↓

5. Verify Disk Space

↓

6. Prepare Restore Target

↓

7. Restore Database

↓

8. Restore Media

↓

9. Restore Config

↓

10. Verify Restore
```

كل مرحلة يجب أن تسجل في السجل (Logs).

---

# نقطة مهمة جدًا

أريد إضافة خطوة لا توجد في كثير من الأنظمة لكنها مفيدة جدًا.

قبل تنفيذ **In-place Restore** يقوم النظام تلقائيًا بإنشاء نسخة احتياطية سريعة من الحالة الحالية.

أي يصبح التسلسل:

```
Current Production

↓

Emergency Backup

↓

Restore Old Backup
```

وبذلك إذا حدث خطأ أثناء الاستعادة يمكن العودة للحالة السابقة.

---

# سجل الاستعادة

كما لدينا `backup_jobs`، أقترح إنشاء جدول:

```
restore_jobs
```

ليسجل:

* نوع الاستعادة.
* النسخة المستخدمة.
* من نفذها.
* وقت البداية.
* وقت النهاية.
* النتيجة.
* سبب الفشل إن وجد.

# بعد اكتمال الاستعادة

لا أريد أن ينتهي النظام برسالة:

```
Restore Completed
```

بل ينفذ تلقائيًا مجموعة من التحققات، مثل:

* هل قاعدة البيانات فُتحت بنجاح؟
* هل عدد ملفات الوسائط يطابق ما في النسخة؟
* هل Manifest يطابق المحتوى؟
* هل يمكن الوصول إلى الملفات؟

ثم يعرض تقريرًا نهائيًا مثل:

```
Restore Summary

Database      ✅
Media         ✅
Config        ✅
Verification  ✅

Status:
SUCCESS
```

## رأيي المعماري

أقترح أن يكون **محرك الاستعادة (Restore Engine)** معكوسًا تقريبًا لمحرك النسخ الاحتياطي الحالي. أي أن كل خطوة في الـ Backup سيكون لها خطوة مقابلة في الـ Restore. هذا يجعل الكود أوضح، ويسهل صيانته واختباره، ويضمن أن دورة **Backup → Restore** تبقى متناظرة وسهلة الفهم للمطورين مستقبلاً.
هذا سؤال ممتاز، ومن المهم أن تفهم ما يحدث قبل تنفيذ أي أمر، خاصة عندما يتعلق الأمر بالاستعادة.

* عدد الملفات

# ماذا سيحدث داخليًا؟

محرك الاستعادة سيبدأ تقريبًا بالتسلسل التالي:

```
استلام الطلب

↓

البحث عن النسخة الاحتياطية

↓

قراءة Manifest

↓

التحقق من سلامة النسخة

↓

فك ضغط الأرشيف

↓

↓

نسخ الملفات إلى مجلد الوسائط

↓

↓
```

# لماذا بدأنا بالوسائط فقط؟

لأنها أقل خطورة.

فلو حدث خطأ:

* لن تُحذف الجداول.
* لن تتغير البيانات.
* سنختبر أن محرك الاستعادة يعمل.
* سنختبر فك الضغط.
* سنختبر قراءة النسخة الاحتياطية.

أي أننا نختبر جزءًا كبيرًا من النظام دون المساس بقاعدة البيانات.

---

# ماذا لن يحدث؟

بسبب:

```json
"restoreDatabase": false
```

فلن يقوم النظام بـ:

* ❌ إسقاط الجداول.
* ❌ استيراد `database.sql`.
* ❌ تغيير أي سجل في PostgreSQL.

---

# ماذا سيحدث للوسائط؟

هنا توجد نقطة مهمة يجب معرفتها.

قبل تنفيذ الأمر، نحتاج أن نعرف **سياسة الاستعادة** في الكود الحالي.

هل يقوم النظام بـ:

### الخيار الأول

```
media-storage

↓

يحذف كل الملفات

↓

ينسخ ملفات النسخة الاحتياطية
```

أم

### الخيار الثاني

```
media-storage

↓

يستبدل الملفات الموجودة فقط

↓

ويضيف الملفات الناقصة
```

أم

### الخيار الثالث

```
media-storage

↓

ينسخ فوق الموجود دون حذف أي شيء
```

هذه نقطة مهمة لأنها تحدد تأثير اختبار **Media Restore** على البيئة الحالية.

**لذلك قبل تنفيذ الأمر، أود التأكد من سلوك محرك استعادة الوسائط.** إذا كان يستعيد فوق المجلد الحالي، فسنعرف بالضبط ماذا نتوقع أثناء الاختبار.
