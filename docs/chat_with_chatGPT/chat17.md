راجعت الخطة كاملة، وبشكل عام **أوافق على تنفيذها**. هي متماسكة وتعالج المشكلة الحقيقية التي واجهتموها. لكن لدي **6 تعديلات صغيرة** أوصي بها قبل البدء، لأن تعديلها الآن أسهل بكثير من تعديل الـ API والـ Flutter لاحقًا.

---

# 1. لا تضع منطق Risk داخل Controller ❗ (أهم ملاحظة)

في الخطة مكتوب:

> BackupController يعيد riskLevel

أنا أوصي أن يكون:

```text
Controller
      ↓
RestoreOrchestratorService
      ↓
RestorePreviewBuilder
```

أي أن منطق:

* diff
* warnings
* riskLevel

يكون داخل Service وليس Controller.

الـ Controller يجب أن يكون رفيعًا جدًا.

---

# 2. لا تستخدم List<String> للتحذيرات

بدلاً من:

```dart
warnings: [
   "ستفقد 21 وحدة"
]
```

اجعلها Structured.

مثلاً:

```json
{
  "warnings":[
     {
        "type":"UNITS_LOSS",
        "severity":"HIGH",
        "count":21,
        "percentage":10.2,
        "message":"ستفقد 21 وحدة"
     }
  ]
}
```

لماذا؟

لأن Flutter قد يحتاج لاحقًا:

* أيقونة مختلفة
* لون مختلف
* ترتيب حسب severity

بدون Parsing للنص.

---

# 3. UNKNOWN أفضل من HIGH

في الخطة:

> إذا لم توجد Manifest Stats

يصبح

```text
HIGH
```

أنا لا أوافق.

الأصح:

```text
SAFE
LOW
MEDIUM
HIGH
UNKNOWN
```

لأن:

عدم وجود البيانات

≠

وجود خطر مرتفع.

---

# 4. أضف نسبة الفرق داخل diff

بدلاً من:

```json
{
   "units":-21
}
```

اجعل:

```json
{
    "units":{
        "difference":-21,
        "percentage":-10.2
    }
}
```

لأن Flutter لن يضطر لإعادة الحساب.

---

# 5. أضف Restore Readiness

أنصح بإضافة:

```json
{
    "canRestore":true
}
```

أو

```json
{
    "canRestore":false,
    "reason":"Manifest corrupted"
}
```

حتى لا يعتمد Flutter على تفسير الـ warnings.

---

# 6. نقطة صغيرة في الـ UI

بدلاً من:

```
[متابعة]
```

إذا كان

```
risk = HIGH
```

اجعل الزر:

```
[أفهم المخاطر وأتابع]
```

أو

```
Continue Anyway
```

ويصبح لونه مختلفًا.

هذا يقلل الضغط الخاطئ على الزر.

---

# شيء أعجبني جدًا

وجود:

```text
statsAvailable
```

فكرة ممتازة.

لكن أنا سأغير الاسم إلى:

```text
hasContentStats
```

لأنها أوضح.

---

# شيء لا أنصح به

كتبت:

```
FutureBuilder
```

إذا أنتم تستخدمون Riverpod في المشروع، فمن الأفضل أن يبقى التدفق متسقًا مع بقية التطبيق باستخدام Provider/AsyncValue بدلًا من إدخال FutureBuilder لهذا السيناريو، إلا إذا كانت شاشة النسخ الاحتياطي أصلًا مبنية عليه.

## القرار

**إذا عدّل فقط هذه النقاط الست، فأنا أقول له: نفّذها.**

خصوصًا:

1. نقل منطق `riskLevel` إلى الـ Service.
2. إضافة حالة `UNKNOWN`.
3. جعل `warnings` كائنات منظمة بدل نصوص.

هذه التعديلات تجعل الـ API أكثر قابلية للتوسع دون تغيير بنيته مستقبلًا.
