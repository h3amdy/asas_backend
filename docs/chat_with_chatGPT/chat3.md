```http

```

```json

  "message": "Restore started",
  "jobUuid": "6d8fca2d-903d-4ff2-97f0-80714d1e1bf4"
}
```

وهذا يعني أن:

* ✅ إنشاء Restore Job يعمل.
* ✅ جدولة العملية تعمل.
* ✅ بدأ تنفيذ محرك الاستعادة.

# أين توقف؟

توقف مباشرة عند أول خطوة:

```
Checksum file mismatch
```

وهذا جيد من ناحية التصميم، لأنه لم يبدأ بنسخ أي ملفات قبل التحقق من سلامة النسخة.

---

# لكن هناك شيء غريب جدًا

رسالة الخطأ هي:

```
Checksum file mismatch:

.sha256 file says

bf6c025892870ebd...

DB says

bf6c025892870ebd...
```

لاحظ أنها تعرض **نفس بداية الـ SHA** للطرفين.

هذا يجعلني أشك أن المشكلة ليست في الـ checksum نفسه.

---

## الاحتمالات الأقوى

### الاحتمال الأول (الأرجح)

الرسالة تقطع الـ SHA إلى أول 16 حرفًا فقط.

قد يكون:

```
file:
bf6c025892870ebd5cdc7c05...
```

بينما

```
DB:
bf6c025892870ebd12345678...
```

أي أن البداية متطابقة لكن النهاية مختلفة.

---

### الاحتمال الثاني

يوجد خطأ في المقارنة نفسها.

مثلًا:

```ts
fileSha.trim()
```

مقابل

```ts
dbSha
```

أو وجود:

* newline
* carriage return
* spaces

في ملف `.sha256`.

---

### الاحتمال الثالث

الـ `.sha256` يحسب شيئًا مختلفًا.

مثلاً:

* DB تخزن SHA لملف `tar.gz`.
* بينما الملف `.sha256` يحسب SHA لمحتوى آخر.

---

# الخطوة التالية

الآن لا أريد تعديل أي كود عشوائيًا.

أريد معرفة سبب المقارنة.

ابحث في الكود عن الجزء الذي يرمي هذا الخطأ:

```
Checksum file mismatch
```

وأرسل الدالة أو الملف الذي يحتوي عليه (حوالي 30–50 سطرًا حوله).

**بهذه الطريقة سنعرف إن كان الخطأ في:**

* إنشاء ملف `.sha256`.
* قراءة الملف.
* أو منطق المقارنة نفسه.

وهذا سيكون أول Bug رسمي في **BKP-002 Restore** وسنعالجه بشكل صحيح قبل الانتقال لاختبار استعادة قاعدة البيانات.
