أرى أن الوقت مناسب للانتقال إلى **المرحلة التالية** بدل الاستمرار في تعديل الـ Backup نفسه.

ترتيبي سيكون كالتالي:

## 1. إغلاق BKP-001 رسميًا ⭐⭐⭐⭐⭐

لم يعد المطلوب تطويرًا، بل توثيقًا.

أنشئ تقريرًا نهائيًا يتضمن:

* المشكلة الأصلية.
* سببها.
* ما الذي تم إصلاحه.
* نتائج الاختبار.

مثلاً:

```
BKP-001 — Backup System

قبل الإصلاح:
Expected: 1006
Copied: 207
Missing: 799

السبب:
MediaProcessingService لم يكن يحدث storage_key بعد التحويل إلى WebP.

الإصلاح:
- إصلاح MediaProcessingService.
- Migration لـ 785 سجل.
- WebP fallback.

النتيجة:
Expected: 1006
Copied: 992
Missing: 14
Status: PARTIAL_SUCCESS
```

---

# 2. التحقيق في الـ 14 ملف فقط

هذه المهمة أصبحت صغيرة جداً.

أنصح بإضافة Log مؤقت:

```
Missing file:
storage_key=...
```

ثم ستعرف هل هي:

* ملفات محذوفة.
* أو سجلات تالفة.
* أو بيانات تجريبية.

قد يستغرق حلها أقل من نصف ساعة.

---

# 3. تنفيذ Restore كامل (الأهم الآن) ⭐⭐⭐⭐⭐

النسخ الاحتياطي لا يعتبر منتهيًا حتى تثبت أن الاستعادة تعمل.

اختبر:

```
Backup
      ↓
Restore
      ↓
تشغيل النظام
```

ويجب التحقق من:

* قاعدة البيانات.
* الوسائط.
* ملفات الإعداد.
* الصلاحيات.
* Checksums.
* Manifest.

إذا نجحت الاستعادة، فأعتبر نظام النسخ الاحتياطي مكتملًا.

---

# 4. تحسينات اختيارية

بعد نجاح الاستعادة يمكنك التفكير في:

* تشفير النسخ الاحتياطية.
* الاحتفاظ بعدة إصدارات.
* النسخ إلى S3 مستقبلاً.
* ضغط أفضل.

لكنها ليست ضمن الـ MVP.

---

## ما أنصح به لمشروع "أساس"

بصراحة، لا أريد أن نقضي أسبوعًا آخر على 14 ملفًا مفقودًا بينما لديك ميزات أكبر تنتظر التنفيذ.

أنا سأعتبر المهمة الحالية منتهية عمليًا، وأنتقل مباشرة إلى:

> **BKP-002: اختبار الاستعادة (Restore) بالكامل.**

إذا نجح الـ Restore، فسيصبح لديك نظام Backup/Restore مكتمل، وهو أحد أهم الأجزاء في المنصة.
