## 1. المقدمة

نظام النسخ الاحتياطي والاستعادة (Backup & Recovery System) هو جزء من البنية التحتية لمشروع **أساس**. يهدف إلى حماية بيانات النظام وضمان استمرارية العمل عند حدوث أي كارثة تقنية.

### 1.1 نطاق الوثيقة

تُحلل هذه الوثيقة:
- ما البيانات التي يجب حمايتها
- سيناريوهات الكوارث المتوقعة
- القرارات المعمارية المعتمدة
- القيود والمتطلبات الأمنية

### 1.2 سياق المشروع

| العنصر | التفاصيل |
|--------|----------|
| **المشروع** | أساس — نظام إدارة المدارس |
| **الباكيند** | NestJS + PostgreSQL + Prisma |
| **الاستضافة** | VPS — استضافة ذاتية |
| **البنية** | Multi-tenant (مدارس متعددة) |
| **تخزين الوسائط** | `/var/data/asas/storage/{school_uuid}/{asset_uuid}/` |
| **لوحة التحكم** | Flutter Admin Panel (Platform Owner فقط) |

## 4. القرارات المعمارية المعتمدة

### ✅ BKP-DEC-001 — Scope of Backup

يدعم النظام في MVP النسخ الاحتياطي والاستعادة لـ:
- ✅ قاعدة بيانات PostgreSQL
- ✅ ملفات الوسائط (Media)
- ✅ ملفات إعدادات الخادم (Server Configuration)

لا يشمل:
- ❌ ملفات التطبيق (Application Code) — تُدار عبر Git
- ❌ ملفات السجلات (Logs)

---

### ✅ BKP-DEC-002 — Backup Strategy (MVP)

يعتمد النظام في الإصدار الأول على **Full Backup فقط**.

- كل نسخة مستقلة وكاملة، لا تعتمد على نسخة سابقة.
- يمكن استعادة أي نسخة مباشرة.
- لا يُدعم Incremental أو Differential في هذه المرحلة.

**المبرر:** سهولة الاستعادة، موثوقية أعلى، مناسب لحجم بيانات المدارس.

---

### ✅ BKP-DEC-003 — Backup Package Structure (مُعدّل)

كل نسخة احتياطية هي حزمة بصيغة **tar.gz** تحتوي:

```text
backup_2026-07-27_23-30-15.tar.gz
│
├── manifest.json          ← بطاقة هوية النسخة + checksums داخلية
├── database/
│   └── postgres.sql.gz    ← pg_dump مضغوط
│
├── media/
│   ├── {school_uuid}/
│   │   └── {asset_uuid}/
│   │       └── variant.ext
│   └── ...
│
└── config/
    ├── .env
    ├── nginx.conf
    └── pm2.config.js
```

**ملفات خارج الأرشيف:**
```text
backup_2026-07-27_23-30-15.tar.gz           ← النسخة
backup_2026-07-27_23-30-15.tar.gz.sha256    ← بصمة الأرشيف
```

**لماذا `tar.gz` بدلاً من `zip`:**
- أفضل أداء على Linux (بيئة VPS المستهدفة)
- يحافظ على صلاحيات الملفات والروابط الرمزية
- لا قيود على حجم الملفات (لا حاجة لـ ZIP64)
- مدعوم أصلاً من أدوات النظام

**مستويا التحقق من السلامة:**

| المستوى | الملف | الوظيفة |
|---------|-------|---------|
| خارجي | `.sha256` | التحقق من سلامة ملف الأرشيف قبل فتحه |
| داخلي | `manifest.json` | التحقق من سلامة كل ملف داخل الأرشيف بعد فك الضغط |
| قاعدة البيانات | جدول `backups` | للإدارة والبحث وعرض الحالة |

**المبرر:** نسخة مكتفية ذاتياً (Self-contained) — يمكن نقلها لأي خادم والتحقق منها دون الحاجة لقاعدة بيانات أصلية.

### ✅ BKP-DEC-004 — Storage Strategy

- تصميم قائم على **Storage Providers** مع تفعيل **Local Storage** فقط في MVP.
- التصميم يسمح بإضافة S3، MinIO، خادم احتياطي مستقبلاً دون تغيير منطق النسخ.

**بنية المجلدات المحلية:**

```text
/var/backups/asas/
├── completed/     ← النسخ الناجحة والمتاحة للاستعادة
├── temp/          ← ملفات مؤقتة أثناء الإنشاء (تُحذف بعد النجاح)
└── failed/        ← نسخ فشلت — للتشخيص (اختياري)
```

### ✅ BKP-DEC-005 — Retention Policy

سياسة احتفاظ قابلة للإعداد:

| الإعداد | القيمة الافتراضية |
|---------|-------------------|
| الحد الأقصى لعدد النسخ | 30 |
| الحد الأقصى للعمر | 90 يوماً |
| حذف تلقائي | نعم |

- دعم **Pinned Backups**: نسخ محمية لا تُحذف تلقائياً
- يُطبق التنظيف بعد نجاح أي نسخة جديدة أو وفق مهمة مجدولة

### ✅ BKP-DEC-006 — Backup Scheduling

| المصدر | الدعم في MVP | ملاحظة |
|--------|-------------|--------|
| Manual Backup | ✅ | زر في لوحة التحكم |
| Scheduled Backup | ✅ | يومي / أسبوعي / شهري |
| Event-based Backup | ❌ | مستقبلي (قبل التحديثات مثلاً) |

- فصل الجدولة عن محرك النسخ (SRP)
- منع تشغيل أكثر من عملية Backup في الوقت نفسه (Concurrency Lock)
- يستخدم `@nestjs/schedule` الموجود فعلاً في المشروع

---

### ✅ BKP-DEC-007 — Backup Encryption Policy (MVP)

- **لا تشفير في MVP** — النسخ تُحفظ محلياً فقط.
- ملفات النسخ تُعتبر بيانات حساسة → تقييد الوصول بصلاحيات نظام التشغيل.
- النسخة تحتوي `.env` كاملاً (بما فيه الأسرار) لضمان استعادة كاملة.
- مسؤولية حماية ملفات النسخ تقع على مدير النظام (Platform Owner).
- التصميم يسمح بإدراج طبقة تشفير مستقبلاً بين مرحلة إنشاء الحزمة ومرحلة حفظها.

```text
Backup Engine → Backup Package → (Encryption Layer - مستقبلي) → Storage Provider
```

**قرار أمني مكمل:** يمكن لمالك المنصة تصدير ملف أسرار مستقل (Export Secrets) كميزة اختيارية لحفظه في مكان آمن خارج النسخة الاحتياطية.

### ✅ BKP-DEC-008 — Backup Consistency Strategy

**المشكلة:** أثناء النسخ قد تتغير ملفات الوسائط — فتصبح قاعدة البيانات غير متسقة مع الملفات.

**الحل:**

```text
Start Backup
    ↓
pg_dump (MVCC Snapshot — متسق تلقائياً)
    ↓
استخراج قائمة الوسائط من الـ dump نفسه (وليس من DB الحية)
    ↓
نسخ ملفات الوسائط وفقاً للقائمة فقط
    ↓
بناء manifest.json
    ↓
ضغط (tar.gz)
```

**حالات النتيجة:**

| الحالة | المعنى |
|--------|--------|
| `SUCCESS` | كل شيء تم نسخه بنجاح |
| `PARTIAL_SUCCESS` | النسخة مكتملة لكن بعض ملفات الوسائط مفقودة |
| `FAILED` | تعذر إنشاء النسخة |

**تقرير التناسق (Consistency Report) في manifest.json:**

```json
{
  "consistency": {
    "databaseSnapshot": "2026-07-27T12:00:00Z",
    "mediaExpected": 1832,
    "mediaCopied": 1830,
    "missingMedia": ["school1/asset1/original.mp4", "school2/asset5/thumb.jpg"],
    "status": "PARTIAL_SUCCESS"
  }
}
```

### ✅ BKP-DEC-009 — Backup Engine Strategy

**القرار الجوهري:**

> أساس ليس محرك نسخ احتياطي (Backup Engine)، بل **نظام إدارة وتنسيق (Backup Orchestrator)** يعتمد على أدوات موثوقة.

| المسؤولية | المنفذ |
|-----------|--------|
| جدولة النسخ | أساس |
| بدء عملية النسخ | أساس |
| نسخ قاعدة البيانات | `pg_dump` (أداة نظام) |
| نسخ الوسائط | `tar` / `rsync` (أدوات نظام) |
| إنشاء manifest | أساس |
| الضغط | `tar` + `gzip` (أدوات نظام) |
| سياسة الاحتفاظ | أساس |
| سجل العمليات | أساس |
| الاستعادة | أساس |

**المبرر:** لا نعيد اختراع ما تقدمه أدوات ناضجة ومجربة. نركز على القيمة الفريدة: الإدارة، التنسيق، التقارير، والاستعادة.

**تصميم قابل للتوسع:**

```text
BackupEngine (Interface)
    ├── PgDumpEngine      (MVP)
    ├── PgBackRestEngine  (مستقبلي)
    └── WalGEngine        (مستقبلي)
```

### ✅ BKP-DEC-010 — Pre-flight Validation

قبل بدء أي عملية نسخ، يتحقق النظام من:

- [x] مساحة القرص المتاحة (يجب أن تكفي لنسخة مؤقتة + نسخة نهائية)
- [x] إمكانية الكتابة إلى مجلد النسخ
- [x] صلاحيات الوصول
- [x] توفر أدوات النظام (`pg_dump`، `tar`، `gzip`)
- [x] إمكانية الاتصال بقاعدة البيانات
- [x] عدم وجود عملية Backup أخرى قيد التنفيذ

**إذا فشل أي فحص → لا تبدأ عملية النسخ** ويُسجل السبب في سجل العمليات.

---

### ✅ BKP-DEC-011 — Backup Authorization

**القرار:**

جميع عمليات النسخ الاحتياطي والاستعادة هي عمليات **بنية تحتية (Infrastructure Operations)**، وتُنفذ حصراً من خلال **لوحة إدارة المنصة (Platform Administration)**.

- ✅ **Platform Owner** فقط يمكنه إنشاء/استعادة/حذف النسخ
- ❌ **مدير المدرسة** لا يملك أي صلاحية متعلقة بالنسخ الاحتياطي
- ❌ المعلمون والطلاب وأولياء الأمور لا علاقة لهم بالنسخ الاحتياطي

**قرار مكمل — Maintenance Mode:**

> يجب وضع النظام في **وضع الصيانة (Maintenance Mode)** قبل بدء عملية الاستعادة، ومنع جميع المستخدمين من الوصول حتى اكتمالها أو إلغائها.

---

### ✅ BKP-DEC-012 — Backup Data Model

نموذج بيانات من **5 جداول** يفصل بين:

- **Plan** = إعدادات (كيف ومتى وأين)
- **Job** = محاولة تنفيذ (قد تنجح أو تفشل)
- **Instance** = نسخة موجودة فعلياً (ملف على القرص)
- **RestoreJob** = عملية استعادة مستقلة
- **Log** = سجل أحداث للتشخيص

لا ترتبط الجداول بمدرسة معينة — النسخ الاحتياطي يعمل على مستوى المنصة بالكامل.

---

### ✅ BKP-DEC-013 — Mandatory Safety Backup Before Restore

- قبل أي عملية Restore، يُنشئ النظام تلقائياً **Safety Backup** كاملة.
- لا يمكن تعطيل هذه الخطوة في MVP.
- إذا فشلت Safety Backup → يُلغى Restore بالكامل.
- إذا فشل Restore → يُستخدم Safety Backup لتنفيذ Rollback.
- Safety Backup تُوسم كـ `SYSTEM_SAFETY` ولا تنشئ Safety Backup أخرى (منع الحلقات).

---

### ✅ BKP-DEC-014 — Selective Restore Support

يدعم النظام الاستعادة الانتقائية:

- ☑ قاعدة البيانات
- ☑ الوسائط
- ☑ الإعدادات

يمكن اختيار أي تركيبة، مع اشتراط اختيار مكون واحد على الأقل. يتحقق النظام من وجود المكون المطلوب في النسخة عبر حقول `contains_*`.
